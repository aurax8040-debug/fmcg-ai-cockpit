面向快消（FMCG）终端执行协同的 AI 经营分析驾驶舱 —— 把「算数」交给 BI、「研判」交给 AI、「拍板与执行」交给人。
AI 产品 · 面试作品 数据驱动经营决策 人机协同 受控 AI（有引用、可追溯）

0 · 一句话定位与产品定义

「发现异常 → 组织证据 → 生成任务 → 执行复盘」的 KA 活动经营闭环。

快消智析平台解决快消销售运营的核心痛点：数据散落在 ERP / POS / SFA 多处，团队「看得见数字、却看不清问题、更追不上执行」。

产品把经营链路拆成一条主流程：数据底座 → AI 研判 → 业务执行 → AI 经营分析。AI 的价值不在算数，而在跨指标判断、证据组织与跟进建议。

数据底座→ AI 研判→ 业务执行→ AI 经营分析
确定性计算（BI / 代码） AI 推断（受控、待验证） 人工决策 / 执行 证据链 / 可追溯
设计红线：AI 不自动下任务、不审批费用、不调整营销资源、不直接认定「经营不合格」——只提示风险、组织证据、建议下一步；最终结论与行动由人负责。

1 · 用户流程（Human Flow）

以「NKA 客户经理 / 经营管理者」为第一视角，六步闭环：

步骤用户动作系统响应产出
① 经营总览打开驾驶舱，看重点活动、POS 覆盖、执行证据覆盖汇总活动清单 + 覆盖/完整度门槛「哪些活动值得跟进」
② 数据底座确认关联键与数据来源、更新时间、完整度展示 KA→活动→门店→日期→SKU 统一键 + 来源标注（真实/模拟）可信的数据上下文
③ AI 研判选中活动，触发「研判 / 核查」返回 facts / gaps / hypotheses / checks / boundaries，逐条带 trace_id有引用的待验证研判
④ 人工确认核对进货价、费用归属，判断假设是否成立展示「待验证」标注，等待人工决策人拍板结论
⑤ 生成任务把确认的核查项转成任务草稿（负责人/截止/证据清单）创建「草稿」任务，状态机推进可下发的执行任务
⑥ 执行复盘补执行证据、完成复盘、回看效果回填证据 → 覆盖度变化 → 再研判标注「效果待验证」证据驱动的经营分析
关键交互约束：AI 建议必须经人工确认后才能创建任务；任务提交「待补证」前必须填证据、置「已完成」前必须填复盘结论。

2 · AI 流程（AI Flow）

三种 AI 能力共用一套「受控研判」内核，统一走 Dify 工作流 + 输出契约校验：

能力触发输入输出
活动研判 /activities/:id/reanalyze选中活动点「研判」该活动受控证据 JSON（facts / metrics / gaps / trace_ids）受控研判（facts、gaps、hypotheses、checks、boundaries、summary）
核查 Agent /agents/investigate输入具体核查问题问题 + 工具规划（活动/门店POS/执行证据/费用）+ 执行 trace多步工具调用后的受控研判
驾驶舱对话 /dashboard/chat当前筛选范围提问scope + metrics + customers + sources + gaps（带 fingerprint）基于当前上下文的有引用回答

Dify 工作流四段式（ka-activity-analysis.yml）

Start
受控证据输入→ Code
证据门槛校验→ LLM
DeepSeek 受控研判→ Code
JSON+引用校验→ End
返回研判
  • 门槛校验（normalize）：校验 data_version 一致、trace_ids 非空，否则拒绝。
  • 受控研判（llm）：deepseek-chat，temperature=0.1，system prompt 强制「只用 evidence_json、不得重算经营数字、每条都要引用 trace_ids、假设标待验证、无库存不判缺货、无对照不称因果增量」。
  • 输出校验（validate）：强制合法 JSON、必填字段齐全、所有 citation 必须来自输入的 trace_ids，未知引用即拒绝整个结果。
失败保护：模型失败 / 输出非法 / 引用越界时，保留确定性指标、不展示任何模板结论，前端明确显示「Dify 尚未配置」或具体错误码。

3 · Context（上下文契约）

AI 的上下文是受控、可版本、可追溯的，不直连生产库。两类上下文：

3.1 活动研判上下文（由 summarizeActivity 确定性生成）

字段内容来源
activity活动 id / 客户 / 名称 / 类型 / 起止 / 计划门店数 / 状态活动计划
completenessPOS 门店覆盖 / 执行证据覆盖 / 是否有成本确定性计算
gate研判准入档位（normal / qualified / blocked）+ 原因覆盖度阈值
facts / data_gaps确定性事实、数据缺口清单确定性计算
metrics前/中/后三期 sales、qty、cost、margin，活动费用、贡献观察POS + 费用
stores每店三期销量 + POS 是否可得 + 证据状态POS + 证据
trace_ids本次可引用的全部证据 ID（引用白名单）去重汇总

3.2 驾驶舱对话上下文（normalizeDashboardContext）

字段说明
scope_fingerprint当前筛选范围指纹，用于区分不同视图的会话
scope日期范围 / 战区 / KA
metrics销售额、利润、毛利率、销量、动销门店、总门店
customers / sources / gaps客户指标、数据源标签、数据缺口（有数量上限防越界）
boundaries / trace_ids固定边界声明 + 引用白名单
统一关联键：KA → 活动 → 门店 → 日期 → SKU。无库存数据时不判断缺货；无有效对照组时只能说「变化观察」。

4 · 状态与状态机

核心状态机是任务生命周期，严格单向推进，非法跳转被拒绝：

草稿→ 已确认→ 执行中→ 待补证→ 已完成
草稿→ 已驳回（终态）
状态含义允许的下一步强制校验
草稿AI 建议经人工确认后生成已确认 / 已驳回必填：活动、标题、负责人、截止日
已确认已下发执行执行中—
执行中执行推进中待补证—
待补证执行反馈待补证据已完成必须填 proof（证据）
已完成复盘闭环—（终态）必须填 review（复盘结论）
已驳回人工否决—（终态）—

其他状态对象

  • 研判记录（analyses）：success / blocked / failed 三态，记录 data_version、问题、角色、结果或错误。
  • Agent 运行（agent_runs）：success / failed，记录工具规划 plan 与执行 trace。
  • 驾驶舱对话（dashboard_chats）：success / failed，附 scope_fingerprint、反馈 decision、关联任务事件。
  • 执行证据（evidence）：新增即推进 data_version，覆盖度随之刷新。
  • 数据版本（data_version）：全局单调递增，任何写入（任务/证据/研判）都递增，保证 AI 结论可对账到某一数据快照。

5 · 守护规则（Guardrails）

规则阈值 / 条件后果
POS 覆盖门槛< 80%阻断经营假设，只允许补数任务
POS 覆盖有限80% — 95%允许有限研判，结论必须标「待验证」
缺模拟成本成本不可得只阻断活动毛利/贡献，不阻断销售观察
缺执行证据覆盖 < 95%只阻断执行质量判断
输出契约缺字段 / 非 JSON / 引用未知 trace_id拒绝整个 AI 结果，保留确定性指标
不可逾越红线：AI 不自动下任务、不审批费用、不调整营销资源、不判缺货（无库存证据时）、不声称因果增量（无有效对照时）。

6 · 风险与对策

风险等级说明对策
模型幻觉 / 引用越界高大模型可能生成未引用结论、编造数字输出契约强制 citation ⊆ trace_ids，越界即拒绝；数字由代码算，模型不重算
数据口径不一致高门店/SKU 在 POS/SFA/ERP 编码不同先做主数据映射，统一关联键，再喂 AI
因果归因误判高把自然波动当活动增量无有效对照组只能「变化观察」，不称增量
证据不足仍下结论中POS/执行覆盖不足时强行判断完整度门槛 + 分级阻断（守护规则）
密钥 / 数据泄露中浏览器持有 Dify 密钥、模型直连生产库密钥只存服务端 .env；模型不直连生产数据库
越权操作中AI 自动下发任务/审批费用人机协同边界：一切写操作需人工确认
样本不足致评测失真低样本 < 20 时指标不可信评测标注「样本积累中」，满 20 才形成首版指标
演示与真实混淆低面试场景把模拟当真实诚信边界：真实样例 vs 匿名模拟 显式标注

7 · 评测体系（Evaluation）

以人工反馈闭环为核心，量化「AI 建议是否被采纳、是否转化为行动」：

7.1 核心指标（summarizeEvaluation）

指标定义口径
采纳率 adoption_rate(直接采纳 + 修改后采纳) / 已评价成功回答越高越好
任务生成率 task_creation_rate已创建任务数 / 被采纳回答数AI→行动转化
任务完成率 task_completion_rate已完成任务数 / 已创建任务数闭环质量
坏例数 bad_case_count修改 + 否决 + 失败越低越好
平均响应时长 average_response_ms成功回答平均耗时体验指标
成功率 successful_runs成功 / 全部运行稳定性

7.2 反馈决策三态

adopted 直接采纳 modified 修改后采纳 rejected 否决（须填原因）

修改后采纳 / 否决必须填原因码 + 说明，形成可归因的坏例库。

首版指标门槛：累计 ≥ 20 条已评价样本才形成「首版指标」；此前统一标注「样本积累中」，避免小样本误导决策。

9 · 技术架构与生产替换路径

层当前（Demo）生产替换
数据读取Mock BI 服务 + 匿名 fixture佳农 BI / 数仓服务账号查询
任务状态本地 JSON（state-store）SFA / CRM 任务 API
证据存储本地 JSON对象存储（OSS/S3）
AI 调用Dify Workflow（DeepSeek）保持 Dify 输入/输出契约不变
密钥服务端 .env（不提交）服务端密钥管理（Vault/KMS）

关键原则：保持页面与 Dify 输入/输出契约不变，只替换数据与状态后端；模型始终不直连生产数据库，密钥只存服务端。
