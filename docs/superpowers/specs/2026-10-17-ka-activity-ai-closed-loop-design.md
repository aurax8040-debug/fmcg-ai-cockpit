# 快消智析：KA 活动 AI 经营闭环设计

日期：2026-10-17  
状态：用户已于 2026-10-17 批准，尚未实施

## 1. 项目定位

本项目是面向佳沛经销商的 AI 经营分析与业务协同 Demo。公司向 KA 商超总部供货，NKA 客户经理对接商超总采购；活动经 KA 总部确认后提报营销部，营销部寻找第三方执行公司，由长促、临促人员在门店执行，战区销售负责跟进。

Demo 的主叙事从“泛化经营大屏/负毛利预警”收敛为：

> 复用佳农现有 BI/数据底座，把 KA 总部活动、门店 POS、ERP 经营数据、第三方执行证据和战区跟进串成“数据底座 → AI 研判 → 业务执行 → AI 经营分析”的闭环。

当前唯一作品为 `http://127.0.0.1:58044/preview/p1/index.html`，已核验其加载脚本与源码目录 `/Users/liuxiaohua/WorkBuddy/2026-10-12-11-47-53/fmcg-ai-analytics` 一致。后续只改这一作品，不合并其他 Demo。

## 2. 为什么要做

现有流程跨越 KA 总部、NKA、营销部、第三方执行公司、促销人员和战区销售。活动计划、费用、执行证据、POS 结果与经营数据分散，容易出现以下断点：

- 总部确认了活动，但门店是否按计划执行缺少统一状态。
- 长促、临促或路演已经投入，但人员到岗、陈列、售价等证据分散。
- POS 显示销量变化，但无法快速分清数据缺口、执行问题和经营问题。
- 活动结束后只有销售汇总，缺少投入、执行和结果的同屏复盘。
- 下一次选店与资源配置依赖人工经验，历史结果难复用。

AI 的价值不是代替人员作最终决定，而是组合多来源证据、指出缺失信息、生成核查顺序、辅助形成任务和复盘结论。

## 3. 目标与成功标准

### 3.1 目标

- 展示一个可信的 KA 活动从总部确认到门店复盘的完整案例。
- 展示结构化经营数据如何通过受控接口提供给 Dify，而非把原始流水上传知识库或让模型直接扫生产库。
- 明确区分规则计算、AI 研判、工作流执行和人工决策。
- 让面试官能看出用户理解经销商经营、跨角色协同、AI 边界与效果评估。

### 3.2 Demo 成功标准

- 当前首页可进入一条匿名 KA 活动案例，并看到其数据来源与完整度。
- 本地模拟 BI 接口返回稳定、可复算的 JSON；关键销售和费用指标由代码计算，不由大模型计算。
- Dify 真实调用模拟 BI 接口，输出“已知事实、数据缺口、原因假设、核查任务、经营建议”五段结构化结果。
- 用户可人工确认或驳回建议，并生成分配给 NKA、营销或战区销售的任务草稿。
- 任务完成后能把执行证据写回 Mock 服务，Dify 二次读取更新后的证据并进入活动复盘，展示活动前后指标与证据边界。
- Dify 或模型不可用时明确提示，不把固定模板伪装成真实 AI 结果。
- 所有真实、匿名模拟和 AI 推断数据在页面上可区分。

## 4. 非目标与边界

- 不连接真实佳农 BI、商超云、ERP、SFA 或第三方执行系统。
- 不重建生产级数据仓库，不实现真实角色权限、审批或消息通知。
- 不声称已证明活动带来因果增量；只做前后变化和证据充分度分析。
- 不推断门店库存。POS 连续无销售只能触发核查，不能自动判定缺货。
- 不让 AI 自动批准费用、停止活动或决定资源投放。
- 不将现有 NKA Excel 以外的模拟数据包装为公司真实结果。
- 不以知识库保存高频 POS 交易明细；知识库仅保存活动制度、执行标准和指标口径等文档。

## 5. 核心用户与职责

- **NKA 客户经理**：维护 KA 总部关系，确认活动、商务政策和客户范围；审核与客户相关的结论。
- **营销部**：提报和配置长促、临促、路演资源，委托第三方执行公司，审核活动投入方案。
- **第三方执行公司/促销人员**：按活动计划在门店执行并提交到岗、陈列、售价、照片等证据。Demo 不为其建立独立账号，只模拟证据回传状态。
- **战区销售**：跟进门店执行，核查异常并回传一线结论。
- **管理者/面试演示者**：查看经营总览、AI 研判、执行进度和活动复盘。

## 6. 主案例

Demo 只突出一个匿名 KA 活动，避免多个浅场景分散注意力。案例流程为：

1. KA 总部确认门店活动。
2. NKA 将活动提报营销部。
3. 营销部配置第三方执行公司、长促/临促或路演资源。
4. 活动开始，POS 按门店 T+1 回流，第三方提交执行证据，战区销售跟进。
5. 规则发现数据缺失、执行状态异常或活动结果未达预期。
6. Dify 汇总结构化证据，给出事实、缺口、假设和核查顺序。
7. 人工确认后生成任务草稿，分配给对应角色。
8. 补充执行证据后，系统复算活动前后销售、毛利、费用和贡献结果。
9. AI 生成复盘摘要与下一次选店/资源配置建议，明确其只是建议。

案例中的 KA、门店、人员和活动名称均匿名化；除现有 NKA Excel 可核实聚合外，其余活动/POS/执行数据明确标为模拟。

## 7. 信息架构与页面改造

保留当前明亮驾驶舱视觉和已有真实 NKA 销售/毛利数据，但将首页从“功能集合”收敛为一条闭环。

### 7.1 经营总览

- 顶部展示四阶段主线：数据底座、AI 研判、业务执行、AI 经营分析。
- 保留销售、毛利等真实 NKA 指标，并显示来源和财年口径。
- 新增“当前重点活动”入口，展示活动周期、门店覆盖、POS 完整度、执行完成度、费用状态和结果状态。
- 原负毛利卡降级为经营异常之一，不作为唯一主叙事。
- 现有客户、销售明细、汇总、品类、预算、POS、SFA 和负毛利诊断等功能不删除，收纳为二级“经营数据/更多分析”入口；主导航和首屏只突出四阶段闭环。

### 7.2 数据底座

- 展示来源状态：NKA Excel、匿名 POS、活动计划、营销投入、执行证据、战区跟进。
- 每个来源显示更新时间、粒度、是否模拟、完整度和可用范围。
- 展示统一主键关系：KA → 活动 → 门店 → 日期 → SKU。

### 7.3 AI 研判

- 只显示由接口返回并可追溯的事实。
- 结果固定分为：已知事实、数据缺口、原因假设、建议核查、禁止推断。
- 每条结论可展开查看数据来源、计算口径和 Dify 运行标识。

### 7.4 业务执行

- 将人工确认后的建议转成任务草稿。
- 任务包括负责人角色、截止时间、核查内容、所需证据和状态。
- 状态至少包括：草稿、已确认、执行中、待补证、已完成、已驳回。
- 任务与证据通过 Mock API 写入本地 Demo 状态存储，保证 Dify 能二次读取；不再只依赖浏览器 `localStorage`。这仍是本地演示持久化，不声称已连接企业工作流。

### 7.5 AI 经营分析

- 活动复盘展示活动前、活动中、活动后的销售与毛利变化。
- 单列活动投入和贡献分析，不与 ERP 基础毛利混为同一口径。
- 展示 POS 完整度、执行证据覆盖率和异常门店处理率。
- AI 输出下一次活动建议，并同时列出证据限制和需要人工确认的事项。

## 8. 数据方案

### 8.1 Demo 数据来源

- **真实样例**：当前 `NKA商超.xlsx` 中已核实的客户级销售与毛利聚合。
- **匿名模拟**：门店 POS 日数据、活动计划、营销资源、第三方执行证据、战区跟进和活动费用。
- **知识文档**：匿名活动执行标准、指标定义和核查规则，用于 Dify 知识检索。

### 8.2 最小数据模型

- `ka_customer`：KA 标识、匿名名称、战区。
- `store`：门店标识、所属 KA、战区；不包含库存字段。
- `sku`：SKU 标识、品类、规格、匿名模拟单位成本；模拟成本只用于匿名活动案例，不与真实 NKA 聚合混算。
- `activity_plan`：活动标识、类型、周期、门店范围、预算和状态。
- `pos_store_daily`：日期、门店、SKU、销量、销售额、成交均价、同步状态。
- `marketing_resource`：活动、资源类型、计划人数/场次、预算和实际费用。
- `execution_evidence`：活动、门店、证据类型、提交时间、核验状态和匿名资源路径。
- `followup_task`：异常、负责人角色、截止时间、所需证据、状态和人工结论。

### 8.3 指标口径

- POS 销售额、销量、成交均价、数据完整度由接口确定性计算。
- 基础毛利沿用现有 ERP/NKA Excel 口径，不把营销费用混入。
- 匿名活动案例使用匿名模拟 SKU 成本计算活动级毛利，再单列“活动级毛利－可归属活动费用”的贡献观察值，并标记为模拟分析口径；真实 NKA 客户级聚合只在经营总览独立展示，不与该活动案例建立真实客户关联。
- 活动效果使用前后窗口变化，同时显示同期/对照是否缺失；无对照时不得写成因果提升。
- 数据不完整时先提示补数或核查，不能继续生成确定性原因。

## 9. 本地模拟 BI 接口

新增独立的本地 Mock API，读取匿名样例 JSON 或 SQLite；不依赖真实佳农 BI。为减少项目依赖，默认使用现有 Node 22 运行时和内置 HTTP 能力。

最小接口：

- `GET /api/health`：服务与数据版本。
- `GET /api/data-sources`：各数据源状态、更新时间、完整度和真实性标签。
- `GET /api/activities`：活动列表和摘要。
- `GET /api/activities/:id/evidence`：活动事实、缺口、前后指标和执行证据。
- `GET /api/activities/:id/stores`：门店级结果与异常标记。
- `POST /api/tasks`：创建 Demo 任务草稿。
- `PATCH /api/tasks/:id`：更新人工确认、状态、结论和负责人。
- `POST /api/activities/:id/evidence`：写入匿名模拟执行证据并更新证据版本。
- `POST /api/activities/:id/reanalyze`：触发后端调用 Dify，确保复盘使用最新证据版本。

响应统一包含 `source_type`、`as_of`、`data_version`、`completeness` 和 `trace_ids`，供页面与 Dify 溯源。

### 9.1 数据完整度与阻断规则

- 缺少活动标识、门店标识、日期或数据版本时，完全阻断经营原因研判，只输出接口错误。
- POS 门店覆盖低于 80% 时，只输出数据缺口和补数任务，不输出经营原因排序或活动效果判断。
- POS 门店覆盖在 80%—95% 之间时，允许生成待验证假设和核查任务，但禁止给出确定性活动结论。
- POS 门店覆盖达到 95% 及以上时，可进入正常研判；仍需结合执行证据完整度显示置信边界。
- 缺少匿名成本时，阻断活动毛利和贡献观察值，但不阻断销售与执行分析。
- 缺少到岗/陈列等执行证据时，不得判断执行好坏，只能生成补证任务。
- 上述阈值为 Demo 产品规则，页面必须显示，可由后续真实业务规则替换。

## 10. Dify 方案

Dify 不直接读取生产数据库。为本项目新建独立的“快消智析·KA活动研判”应用，不改动此前用于连通测试的通用聊天助手。发布可调用版本，并把脱敏后的 DSL/流程说明纳入项目，API 密钥只放环境变量。

Mock API 作为轻量服务加入 Dify 所在 Docker 网络，Dify 通过服务名访问；端口仅以 `127.0.0.1:端口` 映射给 Mac 本机前端。这样既不需要把服务暴露到局域网，也避免 Docker 无法访问只绑定主机回环地址的问题。

建议流程：

1. 开始节点接收 `activity_id`、当前问题和用户角色。
2. HTTP 节点获取活动证据 JSON。
3. 代码节点检查必需字段、完整度和禁推断条件。
4. 可选知识检索节点读取活动标准与指标口径。
5. LLM 节点只基于传入证据生成结构化 JSON。
6. 代码节点校验输出字段和引用的 `trace_ids`。
7. 回答节点返回前端所需结果。

前端不保存 Dify API 密钥。浏览器调用本地后端代理，代理从环境变量读取密钥并调用 Dify。Dify 或模型失败时，页面展示失败原因和原始确定性指标，不自动回退成伪 AI 文案。

AI 输出协议：

- `facts`：只允许引用接口事实。
- `data_gaps`：缺失或延迟数据。
- `hypotheses`：明确为待验证原因。
- `recommended_checks`：按角色生成核查动作。
- `management_summary`：活动经营摘要。
- `boundaries`：库存不可见、因果未证明等限制。
- `citations`：引用 `trace_ids`。

## 11. 规则、AI、工作流与人工边界

- **规则/SQL**：汇总、同比/环比、完整度、阈值、费用计算和异常触发。
- **AI**：跨来源归纳、假设排序、自然语言解释、任务草拟和复盘摘要。
- **工作流**：状态流转、负责人、截止日期、证据要求和操作记录。
- **人工**：确认原因、审批费用、决定资源调整、判断活动是否继续。

任何缺少来源的数字、库存判断、因果结论或自动费用决策都应被输出校验阻断。

## 12. 真实性与安全

- 页面固定显示“真实样例 / 匿名模拟 / AI 推断”标签。
- 不使用真实门店、促销人员、合同或敏感客户明细。
- Dify 输入只发送当前活动的必要汇总证据，不发送全量流水。
- 所有 AI 结果保留运行时间、输入数据版本和引用 ID。
- 本地服务只监听 `127.0.0.1`；不默认公开分享。
- 匿名活动案例使用 `KA-A` 等虚构标识，只与真实 NKA 聚合并列展示，不绑定或影射任何真实客户。

## 13. 验收路径

面试演示控制在约 3—5 分钟：

1. 从经营总览进入一个重点 KA 活动。
2. 查看数据底座及 POS/执行证据完整度。
3. 触发 Dify 真实研判，查看事实、缺口与假设。
4. 人工选择一条建议并生成战区或营销核查任务。
5. 补充一条模拟执行证据，完成任务。
6. 进入 AI 经营分析，查看前后变化、贡献观察和边界说明。
7. 用一句话说明正式落地时 Mock API 可替换为佳农 BI/数仓接口。

## 14. 实现者可自行决定的事项

- Mock 数据具体匿名名称和数值，但必须自洽、可复算且不夸大效果。
- 组件拆分、文件命名、图表细节和局部交互。
- 活动前后观察窗口的默认天数；需在页面明确展示。
- 本地 Mock API 使用 JSON 或 SQLite；优先选择依赖更少、易验证的实现。
- 旧功能在二级入口中的分组与排序，但必须保持可访问并纳入回归检查。
